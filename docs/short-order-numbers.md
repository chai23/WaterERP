# 訂單列印短單號

格式為 `YYMMDD-流水號`，例如 `261117-001`；每日三碼起跳，超過 999 自動延長為 `261117-1000`。日期取台灣建立日期，非配送日期。資料庫交易內分配並以唯一索引保護；取消或變更配送日期不改號。

完整 `order_no` 與所有主鍵、配送、通知、帳務參照保持原值。新增 `short_order_no` 供套印文字與 Code 128 條碼使用，查詢頁優先顯示短號，詳情保留完整單號。沒有短號的舊 API／匯入資料仍可印完整號。訂單查詢、派單搜尋、核銷本頁篩選及發票關聯查詢支援短號。

## 部署

1. 備份資料庫並停止 API，避免升級補號時同時開單。
2. 執行 `npm run db:schema-apply`，套用 `007_short_order_numbers.sql`。
3. 執行 `npm run db:generate`，再執行 `npm run build`。
4. 啟動 API，重新整理後台。

也可使用既有 Windows 啟動器的「更新並部署」流程。Windows 若 Prisma DLL 被占用，須先停用載入該引擎的 API 程序再產生 Client。

遷移會為現有 `sales_orders` 尚無短號的資料補號，依原 SO 長單號中的開單日期排序編配；非標準長號則依 `created_at`（UTC）轉台灣日期。相同日期按建立時間及 ID 排序。遷移可重跑，不改已編配短號，不回退流水號。舊系統歷史訂單資料表不更改。需 MySQL 8 的視窗函式。

其他直接寫入 sales_orders 的匯入腳本如未呼叫配號函式，其短號維持 NULL 並回退完整號；後續補號可在停用 API 時重跑此遷移。不得刪除／重置每日計數器，以免已取消或已刪除訂單的號碼被重用。

## 驗證

`npm run test:short-orders -w apps/api` 建立隔離的本機 MySQL 測試庫，驗證日期邊界、超過 999、舊資料補號與遷移重跑、同時開單、交易回滾、API 現金／月結／預付開單、取消、完整與短號搜尋及最近 100 筆以外的搜尋。測試庫留存供診斷，不修改設定中的原資料庫。

另外執行 `npm run test:cutover -w apps/api` 與 `npm run build` 檢查帳務交接回歸及各前端編譯。紙張與字體座標不因短號更動，實體套印仍需在目標點陣機確認。
